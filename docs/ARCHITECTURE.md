# DevPilot Architecture & Extension Guide

DevPilot provides a deterministic work ledger and audit trail reconciling human and agent contributions across software repositories. It enforces a strict **zero-bullshit rule**: no arbitrary completion percentages ("87% complete") generated by language models.

## 1. High-Level Architecture

```
                  ┌───────────────────────────────┐
                  │    Local Git Repository       │
                  │ (commits, authors, trailers)  │
                  └──────────────┬────────────────┘
                                 │
  ┌────────────────────────┐     │     ┌────────────────────────┐
  │ Exported Issues Track  ├─────┼────►│  Reconciliation Engine │
  │ (JSON / Markdown)      │     │     │   (src/core/reconcile) │
  └────────────────────────┘     │     └───────────┬────────────┘
                                 │                 │
  ┌────────────────────────┐     │                 ▼
  │   Test Run Outcomes    ├─────┘     ┌────────────────────────┐
  │  (JUnit XML / JSON)    │           │ DevPilot Work Ledger   │

                                       └───────────┬────────────┘
                                                   │
                         ┌─────────────────────────┴────────────────────────┐
                         │                                                  │
                         ▼                                                  ▼
                 Terminal / CLI                     Standalone Interactive
                 ANSI Tree View                           HTML Audit
```

## 2. Core Concepts & Taxonomy

### The Three Evidence Tiers
1. **Observed Fact (`observed_fact`)**:
   Empirical, cryptographically or structurally verifiable data from disk or tools:
   - Git commits with specific SHA hashes, authors, and file lists.
   - Test suites executed with passing/failing assertions and recorded runtimes.
   - Formally closed or open issues in local trackers.
2. **Estimate / Heuristic (`estimate`)**:
   Associations inferred by regex matching, keyword heuristics, or unverified branch names.
3. **Human Approval (`human_approval`)**:
   Explicit sign-offs created by human developers via `devpilot approve` with reviewer identity, timestamp, and audit rationale.

### Rigorous Task Statuses
- `VERIFIED_COMPLETED`: Task is closed and backed by passing automated tests and observed commits.
- `IN_PROGRESS`: Observed commits exist, work is underway.
- `TESTS_FAILED`: Associated test assertions failed during execution.
- `NEEDS_HUMAN_REVIEW`: Code was authored solely by an AI agent and has not yet received human sign-off.
- `HUMAN_APPROVED`: Explicit human verification recorded.
- `BLOCKED`: Explicit human rejection or blocker flagged.
- `UNVERIFIED`: Claimed task has no matching commits or tests in the repository.

## 3. Extending DevPilot

The core engine (`src/core/`) is designed to stay strictly under **1,500 lines of code** with zero runtime dependencies.

### Adding a New Test Suite Parser
1. Open `src/core/tests-parser.ts`.
2. Add a parser function converting the runner output into `TestSuiteSummary` and `TestCaseRecord[]`.
3. Register the format in `loadTestResultsFromFile()`.
4. Add deterministic unit tests in `test/tests-parser.test.ts`.

### Adding a New Issue Source Adapter
1. Open `src/core/issues-parser.ts`.
2. Implement your parser returning `IssueRecord[]`.
3. Add fixtures and assertions in `test/issues-parser.test.ts`.
